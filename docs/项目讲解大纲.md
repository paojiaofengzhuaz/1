## P1 封面

- 主标题：直聘通
- 副标题：在线招聘求职平台 —— 基于 Spring Cloud Alibaba + Vue3 的微服务实践
- 底部：答辩人、指导教师、日期（需手动填写）

> 讲稿：这是一个仿 BOSS 直聘的招聘平台，后端做了微服务拆分，前端 Vue3，并接入了 AI 求职助手。

## P2 为什么做这个项目

- 行业痛点：信息不对称、沟通链路长、匹配效率低、简历与岗位割裂
- 项目目标：双角色闭环、沟通前置、多维筛选、智能增强

> 讲稿：招聘的核心矛盾是信息多但匹配慢，所以我们把沟通前置，并用规则匹配 + 大模型两层能力提升效率。

## P3 功能全景

- 求职者：登录注册、职位浏览、关键词搜索、六维筛选、简历维护、投递、在线沟通、智能匹配、AI 助手
- 招聘者：发布 / 下线职位、查看投递、邀面试、回复消息
- 中间连接点：在线沟通

> 讲稿：功能按角色分两栏，中间的“在线沟通”是打通求职者与招聘者的关键环节。

## P4 技术选型

- 微服务底座：Spring Cloud Alibaba 2021.0.5.0 + Nacos（注册发现 / Gateway 网关 / OpenFeign 调用）
- 数据与缓存：MySQL 8（4 个业务库）+ MyBatis-Plus + Redis（Token）
- 前端工程：Vue 3.5 + Vite 6 + Element Plus 2.9

> 讲稿：注册中心选 Nacos，数据按业务垂直分库，前端用组合式 API 便于快速迭代。

## P5 系统架构（重点页）

- 浏览器 → API 网关 18090（路由 + 鉴权 + 身份透传）
- 五个业务服务：user / job / resume / im / match
- 中间件：Nacos 8848、Redis 6379、MySQL 3306
- 服务间调用：match 通过 Feign 读取 job / resume，不直连他人数据库

> 讲稿：前端只认网关，网关做鉴权和路由；服务各自注册到 Nacos；跨服务取数走 Feign，不跨库直连。

## P6 微服务拆分

| 模块 | 端口 | 核心职责 |
|---|---|---|
| recruit-gateway | 18090 | 路由转发、Token 鉴权、透传 X-UserId / X-Role |
| service-user | 18101 | 注册、登录、Token 写入 Redis、用户信息 |
| service-job | 18102 | 职位发布 / 下线、分页检索、行业统计、热门企业聚合 |
| service-resume | 18103 | 简历维护、投递、投递状态流转 |
| service-im | 18104 | 会话、消息、未读数（前端轮询） |
| service-match | 18105 | 匹配打分、AI 求职助手 |
| recruit-common | — | 统一响应、异常、Feign 客户端、DTO |

> 讲稿：按业务边界垂直切分，公共能力下沉到 common，避免各服务重复造轮子。

## P7 数据库设计

- recruit_user：user（账号、角色、公司）
- recruit_job：job（岗位、行业分类、薪资）
- recruit_resume：resume、delivery
- recruit_im：conversation、message
- 数据量：147 岗位 / 28 行业 / 20 城市

> 讲稿：四个库互相独立，跨库查询通过服务接口，而不是连别人的库。

## P8 核心流程一：登录与鉴权

1. 前端提交账号密码 → 2. user 服务校验（MD5）并生成 Token → 3. 写入 Redis（`recruit:token:{token}` = `userId:role`）→ 4. 网关校验 → 5. 透传 `X-UserId` / `X-Role`

设计细节：
- 白名单：登录注册、职位列表 / 详情 / 统计、AI 助手
- 可选鉴权：AI 助手免登录，但带 Token 时仍解析身份
- 下游服务不重复校验，只信任网关请求头

> 讲稿：Token 只在网关校验一次，下游只看请求头，避免每个服务写一遍鉴权。

## P9 核心流程二：职位检索

- 六维筛选：行业 / 城市 / 经验 / 学历 / 薪资区间 / 排序
- 动态条件构造：LambdaQueryWrapper，空值自动跳过
- 薪资取**区间交集**：`job.salary_max ≥ 筛选下限 且 job.salary_min ≤ 筛选上限`
- 排序：最新 / 薪资高低，分页返回 total + records

> 讲稿：薪资不是“包含关系”，而是两个区间求交集，否则 12-20K 的岗位在搜 15-25K 时会漏掉。

## P10 智能匹配算法

| 维度 | 分值 | 规则 |
|---|---|---|
| 基础分 | 30 | 岗位在招即得 |
| 技能命中 | +15/项 | 最多 40 分 |
| 城市一致 | +15 | 期望城市 = 岗位城市 |
| 薪资匹配 | +10 | 期望薪资 ≥ 岗位下限 |
| 学历满足 | +5 | 简历学历等级 ≥ 岗位要求 |

示例：武汉 / 15K / 本科 / 2 年 Java → 字节跳动 Java 开发工程师，95 分，理由 3 条。

> 讲稿：算法不复杂但可解释，每一项加分都有理由，前端能直接展示“为什么推荐”。

## P11 技术亮点：AI 求职助手

链路：前端浮窗 → 网关（可选鉴权）→ service-match → 阿里百炼 qwen-plus（OpenAI 兼容）

三个设计：
1. 人设限定：只答简历 / 面试 / 选岗 / 谈薪，无关话题礼貌拒绝
2. 上下文注入：自动附上当前用户简历 + 各行业代表性岗位
3. 降级兜底：超时或异常回退为规则回复，接口不报错；前端该接口超时放宽到 60 秒

> 讲稿：AI 是加分项不是主链路，大模型不可用时页面依然正常。

## P12 前端工程与交互

- 11 个页面组件：Home、JobList、JobDetail、Publish、MyResume、Deliveries、Chat、Match、Login、AiHelper
- 首页结构：搜索 → 28 行业导航（100+ 二级职能，3 页翻页）→ 热招职位（Tab 切换）→ 热门企业 → 加入我们
- 工程细节：axios 统一拦截（自动带 Token、统一解包 Result、401 跳登录），轻量 reactive 管理登录态

## P13 难点与解决方案

1. 注册中心版本不兼容：nacos-client 2.2 需要 gRPC 9848，本地 1.4.6 连不上 → 改用 Nacos 2.1.0 容器
2. 薪资筛选逻辑：包含关系会漏岗位 → 改为区间求交集
3. 大模型响应慢：默认 20 秒超时被打断 → 单独放宽到 60 秒 + 后端降级
4. 跨服务数据获取：不能直连他人库 → 抽 Feign 客户端 + 共享 DTO

## P14 总结与展望

- 已完成：7 模块微服务架构、双角色闭环、六维筛选 + 匹配打分 + AI 助手、28 行业 147 岗位数据
- 可优化：WebSocket 替代轮询、Elasticsearch 全文检索、MQ 解耦通知、Docker Compose 一键部署 + 链路追踪

## 常见追问与回答

| 追问 | 回答要点 |
|---|---|
| 为什么不用单体？ | 服务按业务垂直拆分，match 这类纯计算服务可独立扩容，故障不互相拖累 |
| Token 为什么放 Redis？ | 多实例共享登录态，网关统一校验，支持过期与主动失效 |
| AI 回答不准怎么办？ | 上下文注入真实简历与在招岗位；失败降级为规则回复，不影响主流程 |
| 数据量只有 147 个岗位，怎么谈性能？ | 重点在架构可扩展性：分页查询、索引（category / city / status）、服务无状态可水平扩容 |
| 消息为什么用轮询？ | 实现简单、依赖少，已列出 WebSocket 作为优化方向 |
