# 选题背景与意义
- 沟通链路长：投递后被动等待，反馈慢
- 匹配效率低：海投简历，人岗错配，双方成本高
- 过程不透明：候选人与 HR 信息割裂，缺少直接对话
- 我们的定位：直聊沟通 + 智能匹配，缩短求职链路

# 需求分析
- 两类角色：求职者（找工作、投简历、沟通）、招聘者（发职位、看简历、沟通）
- 六大功能：登录注册、首页展示、岗位发布、简历投递、在线对话面试、智能匹配助手
- 权限矩阵：岗位发布/投递处理仅招聘者；简历/投递仅求职者
- 越权在网关层透传角色后由业务服务二次校验

# 系统架构与模块拆分
- 客户端层 Vue3（5180）→ 网关层 Gateway（18090）

- 支撑层：MySQL（4 库）+ Redis + 公共模块 recruit-common
- 智能匹配服务通过 Feign 调用岗位与简历服务

# 数据库设计
- 4 个数据库、6 张表，按服务边界拆库，服务自治
- 关系：user 1:1 resume；resume 1:N delivery；job 1:N delivery
- 关系：user(A/B) N:N conversation；conversation 1:N message
- 状态字段：delivery.status（0 待查看 / 1 已查看 / 2 邀面试 / 3 不合适）

# 核心流程①：登录鉴权
- 登录：校验密码 → 生成 UUID Token → Redis 存 userId:role，TTL 2 小时
- 鉴权：网关查 Redis → 命中注入 X-UserId / X-Role 透传下游
- 白名单：登录注册、岗位列表/热门/详情、智能助手
- 退出：删除 Redis Key，Token 立即失效

# 核心流程②：简历投递与状态流转
- 流程：完善简历 → 详情页投递 → 校验简历 → 防重复投递 → 写入记录
- 状态：0 待查看 →（招聘者）1 已查看 / 2 邀面试 / 3 不合适
- 权限：求职者只能投递，招聘者只能处理自己岗位的投递

# 核心流程③：在线对话面试
- 点击「立即沟通」→ 按求职者/招聘者查会话，无则创建、有则复用
- 发送消息：写 message → 更新会话 last_msg/last_time → 对方未读 +1
- 前端 3 秒轮询会话与消息，进入会话自动已读

# 智能匹配算法（核心亮点）
| 维度 | 加分 | 说明 |
| --- | --- | --- |
| 基础分 | 30 | 在招岗位默认分 |
| 技能命中 | 每项 15，最高 40 | 简历技能 ∩ 岗位标签 |
| 城市一致 | 15 | 期望城市 = 岗位城市 |
| 薪资达标 | 10 | 期望薪资 ≥ 岗位下限 |
| 学历满足 | 5 | 学历等级比较 |

- 封顶 99 分，并输出可解释的匹配理由
- 实测：demo 简历 vs Java 后端岗 → 99 分，4 条理由
- 智能助手：自然语言分词 → 岗位文本检索 → 生成推荐话术

# 难点与解决
- ①匹配服务启动失败（Failed to configure a DataSource）
  原因：公共模块带 MyBatis-Plus，无库服务也被要求数据源
  解决：排除 DataSourceAutoConfiguration 与 MybatisPlusAutoConfiguration
- ②网关白名单过宽
  原因：放行所有 GET /job/**，/job/my 拿不到用户头
  解决：精确到 /job/list、/job/hot、/job/{数字}，其余强制鉴权
- ③Feign 调用稳定性
  解决：连接 5s / 读取 10s 超时 + 返回码统一校验
